# Phase 8: Order Assistant

[← Development plan](README.md) · Previous: [Phase 7](phase-7-llm-agents.md) · Next: [Phase 9](phase-9-demo-readiness.md)

**Goal:** a read-only chat app in Work Zone that answers questions about cases with data cards and deep links, instead of a phone call to another team (§5.3, §6.2, scenario 6). It is **not a sixth agent**: it makes no recommendations and has **no path to any action**.

Difference to TM Assistant in the TM project: no `@cap-js/agents`, no A2A, no approval cards, no actions. One OData action `ask` and read-only tools only.

## 8.1 `OrderAssistantService` (`srv/assistant-service.cds` + `.js`)

- [ ] `@requires: ['Sales', 'SupplyPlanner', 'ProductionPlanner']`, path `/odata/v4/assistant`.
- [ ] Action `ask(conversationId, caseId, message)` returns `{ conversationId, answerText, verified, cards, links }`. Action `newConversation(caseId)`.
- [ ] `MyConversations` / `MyMessages`: read-only projections on `ChatConversation` / `ChatMessage` filtered to the owner.
- [ ] Read-only tools in `srv/lib/assistant-tools.js`, each with a strict JSON schema (`strict: true`, `additionalProperties: false`), each checking `canRead(user, case)` first (unauthorized → "not found"):
  - `listCases(filter)`: lane, status, waiting-for role, penalty risk, date range
  - `getCase(caseId)`: header, status, waiting for, latest recommendations and decisions
  - `getCaseTimeline(caseId)`: the `CaseTimeline` view
  - `getSupplyPicture(caseId)`: the stored A3 snapshot
  - `getCapacityOptions(crId)`: the stored A4 options, load before/after, scores, override flags
  - `getSalesOrder(so)`: through `srv/lib/s4/`
- [ ] The tool registry is a fixed list with **no write tool**. The assistant module must not import `orchestrator.js` (ESLint rule).
- [ ] `runToolLoop()` in `srv/lib/llm/`: manual loop in CAP, `tool_choice: auto` (forced tool choice returns 400 on Opus 5.5 / Sonnet 5.5), at most `PlanningParameters.maxToolCallsPerQuestion` (6) tool calls, all parallel tool results returned in one user message, masking on the tool results. In mock mode, a scripted plan maps the scenario 6 questions to tool calls, so the assistant works without a key.
- [ ] **Cards and links are built in CAP from this turn's tool results**, not from LLM text: case header card (ID, lane, status, waiting for, requested / confirmed date), table card (material tree or capacity options), deep links to the case app that fits the user's role ("Open FC-0001 in Supply Planning Workbench").
- [ ] Guards:
  - number check over this turn's tool results; on failure the answer is *"I couldn't verify this answer. See the data below."* and `verified = false`
  - out-of-scope question → *"I can only answer questions about order feasibility cases."*
  - LLM unavailable → no text, only the cards for the case ID found in the question
  - action request ("Confirm FC-0001 to the customer") → explains it can't act, gives the current status from `getCase`, links to the case app; no status change and no audit row
- [ ] Store each turn in `ChatMessage` (question, answer, tool calls, model ID, tokens). Cleared on app restart (demo retention).
- [ ] Check by hand in the Order Assistant app: the three scenario 6 questions as `srini` and `satish`, a question about a case the user may not see, and an action request.

## 8.2 Chat UI: Order Assistant (`app/order-assistant/`)

- [ ] UI5 freestyle app (a chat doesn't fit a Fiori elements floorplan), TypeScript like the other apps: `sap.f.DynamicPage` with a message list, an input and a send button.
- [ ] Each answer is labelled **"Generated by AI, check the data cards"**. Cards and deep-link buttons are rendered from the `cards` / `links` JSON. Answer text is plain text or sanitized Markdown (`sap.ui.core.HTML` with `sanitizeContent: true`, as in the TM project).
- [ ] Suggested questions as chips when the conversation is empty (*What's blocking FC-0001?*, *Show my HIGH cases waiting for me*, *Which cases have penalty risk this week?*).
- [ ] Opened with `?caseId=FC-0001` (from the *Ask about this case* button in the case apps), the case is shown as context at the top.
- [ ] *New conversation* button; busy indicator and locked input while `ask` runs. Enter sends.
- [ ] The name is always **Order Assistant**. Never "copilot".
- [ ] Relative data source URI (`odata/v4/assistant/`), the `/<app-id>` prefix stripped by `server.js` locally, and a `watch-order-assistant` npm script.
- [ ] Wire the *Ask about this case* buttons in the three case apps to the inbound `OrderAssistant-ask` with the `caseId` parameter.

## 8.3 Deployment (commands run by the user)

- [ ] `manifest.json`: `sap.cloud.service` and the inbound `OrderAssistant-ask` (title "Order Assistant").
- [ ] `app/router/xs-app.json` and the app's own `xs-app.json`: route for `odata/v4/assistant`.
- [ ] `mta.yaml`: add the `order-assistant` html5 module and its zip to the app deployer.
- [ ] Commands for the user: `mbt build`, then `cf deploy …`.
- [ ] Work Zone: refresh the HTML5 Apps provider, add **Order Assistant** to all three groups and the Everyone role, then check it in the site.

**Exit criteria:** scenario 6 works in the Work Zone site: *"What's blocking FC-0001?"* as Sales (waiting for Production on CR-0001, two options, O-ALT recommended, case card, link), *"Compare the options for CR-0001"* as Production (table card, O-MOVE "needs override", link), and *"Confirm FC-0001 to the customer"* changes nothing (status and audit log unchanged). The assistant also works in mock mode without a key.
