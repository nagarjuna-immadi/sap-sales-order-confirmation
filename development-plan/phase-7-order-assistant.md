# Phase 7: Order Assistant

[← Development plan](README.md) · Previous: [Phase 6](phase-6-llm-agents.md) · Next: [Phase 8](phase-8-cal-setup.md)

**Goal:** a read-only chat app that answers questions about cases with data cards and deep links, instead of a phone call to another team (§5.3, §6.2, scenario 6). It is **not a sixth agent**: it makes no recommendations and has **no path to any action**. Built and checked locally; phase 9 deploys it to Work Zone with the other apps.

Built like the TM Assistant in the TM project (`sap-cap-tm-dispatch-cockpit`: `srv/agents/dispatch/`, `app/assistant/`): a CAP service with `@agent` from `@cap-js/agents`, served over A2A, and a UI5 freestyle chat on an A2A client. Differences to the TM Assistant: **no actions and no approval cards**, **no token streaming** (progress steps only, the answer appears once it is checked), one assistant instead of one agent per role, and data cards built in CAP. The plugin itself, `cds.requires.llm`, masking and the number check are already set up for A2–A5 in phase 6.

## 7.0 Spike: what the plugin must do

Phase 6.0 already checked `srv.chat`, `emit_data_part`, masking and the middleware hook. These points matter only for a chat with users. Checked 2026-10-06 (`@cap-js/agents` 0.9.7, `claude-haiku-4-5-20251001`) under `--profile hybrid` with a throwaway service. Five points hold as planned; the cards (point 3) need another route, which keeps the design (cards built in CAP, sent as `data-*` artifacts):

- [x] `cds.agents.streaming: false`: no `thinking-*` or token artifacts; the `status-update` progress texts still arrive (*"Querying Cases"*, *"Calling getCase"*, *"Processing tool response"*), and the answer arrives as one `response` artifact. The agent card still says `streaming: true`, so the client uses `message/stream` and gets the progress live.
- [x] A middleware added with `srv.after('buildMiddleware', …)` on an AGENTS.md agent can replace the final answer: its `afterModel` hook returns a message with the **same ID** as the last AI message (no tool calls), the graph state replaces it, and the `response` artifact carries the replaced text. The replaced text is also what stays in the conversation.
- [x] ⚠ A function that returns `{"kind":"data","data":{…}}` does **not** reach the client: the plugin sends function results to Claude as TOON text, and the executor looks for the JSON text `{"kind":"data"` in the tool messages. Publishing on the plugin's event bus from the handler fails too: the handler runs in a CAP context of its own, without `agent.eventBus`. **Works:** a `wrapToolCall` middleware keeps the plugin's context in an `AsyncLocalStorage`, and the handler publishes its cards through it as an `artifact-update` `data-card-<uuid>` (`srv/agents/order-assistant/cards.js`). The cards go to the app once, in the task that produced them, and never through Claude. (The executor's own scan of all tool messages would also re-send earlier turns' data parts; this route avoids that.)
- [x] The query tool runs with the user's identity: a `before READ` handler sees `sales_user` / `production_user` with their roles and filters the rows (FC-0002 without a CR is not listed for `production_user`).
- [x] Masking resolves the pseudonyms in the answer the user sees (Claude gets `customerName-81944…`, the answer says "ABC Automotive"). **Fix needed:** `fixMasking` let only the service's functions and `emit_data_part` through the masking, so query results reached Claude unmasked; `query` is now in that list (`srv/lib/agent-masking.js`; A2–A5 have no entities, no change for them).
- [x] A conversation (`contextId`) of one user cannot be continued by another: the plugin stores checkpoints per user (`createdBy`), so `production_user` with `sales_user`'s `contextId` starts with an empty history, and `sales_user`'s conversation is untouched.
- [x] Also measured: about 8 graph steps per model turn (the middleware hooks are graph nodes), so `recursionLimit: 60` allows about six tool rounds; at the limit the task fails (`GraphRecursionError`).

## 7.1 `OrderAssistantService` (`srv/agents/order-assistant/`)

Folder `srv/agents/order-assistant/`, next to A1–A5: it is a CAP agent like A2–A5, but not a case agent. Pulled in by `using from './agents/order-assistant/order-assistant-service'` in `srv/agents.cds` (CAP loads only the `.cds` files directly in `srv/`, as `srv/agents.cds` in the TM project).

- [x] Configuration: the phase 6 `cds.requires.llm` and `cds.agents` (`streaming: false`, `masking: true`). Added `recursionLimit: 60` (7.0) and the per-user quotas `maxConcurrentTasksPerUser: 2`, `maxTasksPerHourPerUser: 60`, `maxIncomingMessageLength: 2000` (longer messages get a 400 with the reason). They are checked when an A2A request starts, so they don't apply to A2–A5 (`srv.chat`). `maxLLMCallTimeout: 60s` is set as well, but the plugin reads it only for the AI Core model kind; with `kind: anthropic`, `maxExecutionTimePerTask` (2 min) is the limit. A model of its own only through `cds.requires.llm-assistant` and `@agent.llm`, if phase 10 shows the need.
- [x] `order-assistant-service.cds`: `@path: 'order-assistant'` (served at `/a2a/order-assistant`), `@requires: ['Sales', 'SupplyPlanner', 'ProductionPlanner']`, `@agent`, `@agent.connect: 'none'`. A doc comment on the service and on every element and function: that is what Claude reads. Notes for developers go in line comments.
- [x] **No actions on the service**, so nothing can pause for approval and nothing can change. ESLint rule (`eslint.config.mjs`): nothing in `srv/agents/order-assistant/` may import from another agent folder, in particular not A1's `orchestrator.js`. Shared code moved to `srv/lib/` for this: `case-snapshots.js` / `.cds` (the A3 supply picture and the A4 options with their CDS types, now also used by the A3 and A4 agent services), `deep-links.js` (the case-app intents, also used by A5) and `allowedActions()` in `case-view.js`.
- [x] Read-only projections for the query tool, with explicit columns, code lists flattened to their codes (the doc comments name the values) and `caseId` on every entity: `Cases`, `CapacityRequests`, `Recommendations`, `CaseTimeline` (with its durations). No prices (`penaltyAmount`, order value). `@PersonalData.IsPotentiallyPersonal` on customer name and ID. Also left out, because they may carry customer data: the case summary, the customer draft, the audit payload, the recommendations of kinds other than supply and capacity options, and user IDs (`actor`, `decidedBy`).
- [x] Every projection filtered by the read rule of `srv/lib/case-access.js` (rule 8): `caseId in (cases the user may see)`. The functions check `canRead`; a case the user may not see is "not found".
- [x] Functions (each also checks `canRead`), each returning the facts and sending the cards and links:
  - `getCase(caseId)`: header, status, waiting for and since when, next actions (button and app from the case rules), capacity requests with option counts, the latest supply and capacity recommendations and the decision trail from `AuditLog`
  - `getSupplyPicture(caseId)`: the stored A3 snapshot
  - `getCapacityOptions(crId)`: the stored A4 options, load before/after, scores, override flags
  - `getSalesOrder(so)`: through `srv/lib/s4/`; Sales sees every order, the planners only orders with a case they may see
  - added: `getMyContext()`: the user's roles and case apps, today and this week's Monday and Sunday, for "my cases" and "this week" (Claude must not compute dates)
- [x] **Cards and links are built in CAP from the tool results**, not from LLM text (`cards.js`): case header card (ID, item, lane, status, waiting for, requested / confirmed date, penalty risk), table cards (supply options and material tree, capacity options, sales order items, and the case list of a query on `Cases`, whose rows open the case), deep links to the case apps of the user's roles that may read the case ("Open FC-0001 in Supply Planning Workbench"; Production opens the active CR). The assistant has no `emit_data_part` tool, so no card can come from Claude.
- [x] Persona in `AGENTS.md` next to the `.cds` file (`order-assistant.v1`), skills `case-status` and `option-comparison` (their `metadata.examples` are the agent card's examples, which the app shows as chips). It states: read-only, numbers only from this turn's tool results, out-of-scope questions get *"I can only answer questions about order feasibility cases."*, action requests get the current status, the button and app from `nextActions`, and the link.
- [x] Number check (`answer-check.js`, added in `order-assistant-service.js` with `srv.after('buildMiddleware', …)`): `srv/lib/number-check.js` on the final answer against the results of this turn's function and query calls (the skills and the describe tool don't count). On failure the answer becomes *"I couldn't verify this answer. See the data below."* before it is sent; logged with `cds.log('order-assistant')` (with `DEBUG=order-assistant` also the masked text). The number check now also knows times (`16:45` against a fact `…T16:45:22Z`) and dates inside ISO timestamps, which A2–A5 benefit from too. The runs are in `cap.agent.Tasks` (`agentService` = `OrderAssistantService`; the A2A handler sets their final state).
- [x] LLM unavailable: the task fails (checked with a wrong key: state `failed`, the key not in the log); the app shows a plain error and, opened from a case, the link to that case app.
- [x] In development (`llm-mock`) the assistant answers with the plugin's mock text and the result of a query on `Cases` (and its table card), which proves the wiring. Real answers need the key (`--profile hybrid`).
- [ ] Check by hand in the Order Assistant app: the three scenario 6 questions as `sales_user` and `production_user`, a question about a case the user may not see, and an action request. (Checked on the A2A protocol, see 7.3; not yet in the browser.)

## 7.2 Chat UI: Order Assistant (`app/order-assistant/`)

Started from a copy of the TM `app/assistant/` (`model/a2a.ts`, `model/markdown.ts` with vendored `marked`, the controller and view). App ID `order.conf.orderassistant`.

- [x] Removed the agent picker and the approval card. One assistant, one conversation.
- [x] No token bubbles: `onStatus` shows the progress steps in the status line under the conversation; no `onStep`. The answer is rendered when the task completes. Stop cancels the task (`tasks/cancel`; the task ends `canceled`).
- [x] `a2a.ts` reads the `data-card-*` artifacts (each card key once per answer; other data artifacts are ignored) and the app renders cards and deep-link buttons under the answer.
- [x] Each answer is labelled **"Generated by AI, check the data cards"**. Answer text as sanitized Markdown (`sap.ui.core.HTML` with `sanitizeContent: true`).
- [x] Suggested questions as chips when the conversation is empty, from the agent card's skill examples (*What's blocking FC-0001?*, *Show my HIGH cases waiting for me*, *Which cases have penalty risk this week?*, *Compare the options for CR-0001*).
- [x] Opened with `caseId` (from the *Ask about this case* button, or `?caseId=FC-0001` on `index.html`), the case is shown as context at the top and goes with each message as `[Opened from case FC-0001]`.
- [x] *New conversation* button (new `contextId`). Enter sends, Shift+Enter adds a line. Input locked while a task runs.
- [x] The name is always **Order Assistant**. Never "copilot" (`npm run check:wording`).
- [x] Relative data source URI (`a2a/order-assistant/`), the `/<app-id>` prefix stripped by `server.js` locally (now also for `/a2a/`, with the Basic challenge on a 401 and `no-transform` on the event stream, as in the TM project), and a `watch-order-assistant` npm script.
- [x] `manifest.json`: the inbound `OrderAssistant-ask` (title "Order Assistant", optional parameters `caseId`, `crId`, `source`).
- [x] *Ask about this case* in the three case apps opens `OrderAssistant-ask` with `caseId` (Production also `crId`) and `source` (the case app's intent, for the link back when an answer fails). In the launchpad through the Navigation service; locally (each sandbox launchpad knows only its own app) in the Order Assistant's sandbox launchpad. The assistant's deep links work the same way the other direction.
